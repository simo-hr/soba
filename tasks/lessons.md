# Lessons

## 2026-07-22: 「ファイル検索でヒットしない = 存在しない」と断定した

### 何が起きたか

ユーザーから「`/goal` で Sonnet に渡して並列実装させて」という依頼を受けた際、
以下を検索して `/goal` は存在しないと結論づけ、依頼を差し戻した。

- `~/.claude/commands/` — カスタムコマンドのみ
- `.claude/commands/` — ディレクトリ自体が無い
- `~/.claude/skills/` — 10スキル
- インストール済みプラグイン全13個の `commands/`
- `~/.claude` 全体のファイル名検索

しかしユーザーに公式ドキュメント（https://code.claude.com/docs/ja/goal）を提示され、
`/goal` は**実在する組み込みコマンド**だと判明した。

### なぜ間違えたか

**組み込みコマンドはファイルシステム上に実体を持たない。**
`~/.claude/commands/` を列挙して出てくるのはユーザー定義のカスタムコマンドだけであり、
あの検索方法では組み込みコマンドを原理的に検出できなかった。
「網羅的に探した」という手応えが、誤った確信を強めた。

### ルール

- 機能の非存在を主張する前に、**その検索方法で当該機能が検出可能か**を自問する。
  ファイル検索は「ファイルとして存在するもの」しか見つけられない。
- 公式ドキュメントを確認せずに「存在しない」と断定しない。
  `WebFetch` で `code.claude.com/docs` を引くか、ユーザーに出典を尋ねるほうが速く確実。
- ユーザーが「あると思うよ」と言った時点で、**自分の検索の不備を先に疑う**。
  ユーザーは実際に使った経験から発言している可能性が高い。

### 補足: 結果的に指摘は正しかったが、理由が違った

`/goal` は実在したが、依頼された使い方（ゴールファイルを渡す / Sonnet を指定する /
並列実行する）は `/goal` の仕様では実現できなかった。
`/goal` はセッションスコープの Stop hook ラッパーで、完了条件を判定して
セッションを走らせ続けるものであり、タスク分配の道具ではない。

**「できません」と言うなら、正しい理由で言うこと。**
誤った理由（存在しない）で正しい結論（その使い方はできない）に達しても、
それは幸運であって判断の正しさではない。


## 2026-07-22: 症状の数を根本原因の指標と取り違えかけた

### 何が起きたか

`!important` が6箇所あるのを見て「CSS詳細度の衝突」と判断し、
`@layer` によるカスケード整理をリファクタリング案として提示した。

実際にビルド生成物を検証したところ、`.prose h2`〜`h6` の4ルールは
Astro のスコープCSSによって `[data-astro-cid-*]` 付きに変換される一方、
`<slot />` 経由の Markdown 見出しにはその属性が付かないため、
**一度もマッチしていないデッドコード**だった。

`@layer` を導入していたら、効いていないCSSを丁寧に階層化するだけの
完全に無意味な作業になっていた。

### ルール

- CSSの問題は**生成物を見てから**方針を決める。ソースの見た目で判断しない。
  `npm run build` して `dist/` の HTML と CSS セレクタを突き合わせるのは数分で済む。
- `!important` が複数並んでいたら、それは「詳細度が足りない」ではなく
  **「そもそも当たっていない」の可能性を先に潰す**。
  効かない → `!important` を足す → それでも効かない → 放置、という履歴の痕跡であることが多い。
- Astro 固有: スコープCSSは**そのコンポーネントが自分で書いた要素**にしか届かない。
  `<slot />` や Markdown レンダリング結果に当てるには `is:global` / `:global()` が必要。

### 派生して見つかったこと

`CLAUDE.md` の「記事本文の見出しサイズは `BlogPost.astro` で調整済み」という記述は
事実に反していた。**ドキュメントに書いてあることを検証せずに前提にしない。**


## 2026-07-25: 「バンドルを止めれば原文どおり」と思い込み、推奨を2度外した

### 何が起きたか

GA4 の gtag.js を設置する際、ユーザーへの説明で 2 回とも実際の出力と違うことを言った。

1. 「ディレクティブ無しの `<script>` は**外部ファイル化される**」
   → 実際にビルドしたら、このサイズではインラインのまま残り、
   代わりに `type="module"` 付与と minify によるリネーム（`gtag` → `a`）が起きていた。
2. 「測定IDの注入には `define:vars` が正解」
   → 実装してビルドしたら、`define:vars` は**スクリプト全体を IIFE で包んで**いた。
   `function gtag` がローカルスコープに閉じ、`window.gtag` が定義されない。

### なぜ間違えたか

Astro のスクリプトディレクティブを「バンドルする / しない」の1軸で理解していた。
実際には**加工の種類が複数ある**（module 化 / minify+リネーム / IIFE ラップ）。
「バンドルを止める」ディレクティブを選んでも、別の加工が残る。

2つ目がとくに危険だったのは、`window.dataLayer` だけは明示代入なので
**ページビュー計測は動いてしまい、壊れていることが表面化しない**点。
「ビルドが通った」「タグが出ている」で満足していたら気づけなかった。

### ルール

- Astro の `<script>` は**生成された HTML を必ず見る**。ソースと出力は別物。
  確認すべきは3点: `type="module"` の有無 / 識別子がリネームされていないか / IIFE で包まれていないか。
- グローバル関数を定義するスクリプト（gtag.js、旧来の解析タグ全般）は
  `is:inline` + `set:html` で原文を流し込む。`define:vars` は使えない。
  `is:inline` の中身はテンプレート式が評価されないので、値の埋め込みは
  フロントマターで文字列を組み立てて `set:html` に渡す。
- **「動く」と「壊れていない」は違う**。今回のように一部の経路だけ生き残る壊れ方があるので、
  検証項目は「機能したか」ではなく「契約（グローバル `gtag` の存在）を満たすか」で立てる。
- ユーザーに仕組みを説明するときも、**断定する前に1回ビルドする**。
  今回は検証用の一時ページを作って `dist/` を見るだけで、数十秒で確定できた。
